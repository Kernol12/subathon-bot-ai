## 1. Scope and selected approach

One contributor-edited UTF-8 JSON catalog supplies stable message IDs, English and
German templates, declared named parameters and explicit plural forms. A standard-
library Python >=3.10 build tool generates Qt Linguist .ts, actual compiled .qm,
and browser JSON. Qt LinguistTools is a BUILD component of the already selected
Qt dependency, not a new runtime translation library. No npm/Python package,
gettext server, hosted translation service or ICU message-expression dependency is
introduced by this slice.

The SAME named-template grammar survives in Qt and browser outputs. Qt chooses a
stable ID and plural form; a later bounded adapter performs named substitution.
Do not convert names to positional arguments or chain QString::arg. Direct
QTranslator::translate returns the selected raw translation; QCoreApplication and
qtTrId additionally replace %n. That distinction permits literal `%n`, `%1`, `%L1`
and `%%` without escaping tricks. It is supported by the selected Qt6.12 source;
actual compiled-file/runtime tests remain required below. Qt neither reads this
source JSON nor interpolates the named parameters natively.

This defines catalog/generator behavior and downstream adapter obligations only.
LOCALE-002/003 retain detection, saved choices, immediate switching, actual Qt/QML/
browser consumption and independent number/date/currency preferences. LOCALE-004
retains Light/Dark/System; LOCALE-090 retains real German layout/platform evidence.
Built-in labels and structured server message IDs use the catalog. Streamer-
authored scene, viewer design, milestone and chat content is never translated by
this mechanism. No language change alters another user or the broadcast scene.

## 2. Authoritative source shape

Proposed sole source: localization/messages.json. New directories/files are not
created by this document. Root object has EXACTLY:

| Member | Required value |
| --- | --- |
| schema_version | JSON integer1, never true, decimal1.0 or string |
| license | string GPL-3.0-or-later |
| source_locale | string en |
| locales | array ["en","de"] in that order |
| messages | nonempty array of message objects, each ID unique |

Each message has EXACTLY id, description, parameters, plural and translations:

- id: ASCII `[a-z][a-z0-9]*(?:[._][a-z0-9]+)*`, at most160 bytes. It is the
  stable identity, independent of English wording, source path or translation.
  Equal duplicate IDs are rejected too. Never derive IDs from English hashes or
  silently rename/delete/alias them when wording changes. Compatibility/removal
  requires an explicit owning change; this generator does not infer rollout policy.
- description: nonempty translator-facing text, at most4096 UTF-8 bytes. It is
  emitted only as Qt translator context, not as product UI.
- parameters: object mapping zero..32 distinct ASCII names
  `[a-z][a-z0-9_]{0,31}` to EXACT strings text or integer. Object order is irrelevant.
- plural: null for an ordinary message, otherwise the name of ONE declared integer
  parameter. No ordinal/range/fractional/select/offset syntax exists in v1.
- translations: object with EXACT keys en and de. An ordinary locale value is
  `{ "text": "template" }`; a plural locale value has EXACTLY one and other string
  keys. All template strings are nonempty, with the grammar below. Both languages
  have complete required forms before invoking Qt; lrelease's normalization is
  not a substitute for validation.

No unknown members, null translations, inherited locale, unfinished marker or
runtime-authored-content field is accepted. JSON duplicate OBJECT KEYS are errors
at every depth, not a last-value-wins override. Raw source message order and JSON
whitespace/key order do not affect generated bytes. Messages sort by ASCII ID;
parameter names sort by ASCII name; declared plural order is one then other.

All strings preserve Unicode scalar values exactly, with no NFC conversion,
case folding or locale-dependent sorting. Reject invalid UTF-8, a leading BOM,
unpaired surrogate escapes, U+0000 and characters outside XML1.0 Char: TAB/LF/CR,
U+0020..D7FF, U+E000..FFFD and U+10000..10FFFF. Do not silently replace unsupported
controls. Ordinary quotes, ampersands, angle brackets, umlauts, combining sequences,
emoji, CR/LF/TAB and private-use characters remain representable data.

Engineering ceilings: source file <=4MiB before JSON parsing; <=8192 messages;
<=32 parameters/message; <=65536 UTF-8 bytes/template; description/ID/name limits
above; JSON structural nesting <=8. Malformed/unbounded nesting must become a
bounded validation error, never an uncaught parser recursion traceback. These are
local build-input resource limits, not limits on domain money, score or contributions.

## 3. Named templates and lossless integer plural selection

Templates are plain text with these tokens only:

| Source spelling | Meaning |
| --- | --- |
| {name} | insert the supplied declared named value |
| {{ | literal opening brace |
| }} | literal closing brace |
| any other Unicode scalar | literal character, including every percent character |

Unmatched braces, `{}`, unknown names, nested placeholders, format conversions,
Python expressions, ICU syntax and whitespace inside a name are invalid. Repeated
parameters and language-specific reordering are allowed. Each non-selector declared
parameter must appear in EACH form; no undeclared placeholder is accepted. A plural
selector is required as input even when a translator omits its visible placeholder
in one/all forms. Its use as a selector accounts for that declaration.

The downstream named formatter must scan the chosen template once, substitute DATA
once and never rescan inserted arguments. It rejects missing/extra arguments and
wrong parameter types before producing output. text arguments are already-formatted
Unicode text; integer arguments are lossless canonical signed64 DECIMAL STRINGS:
`0`, positive without leading zeros, or `-` plus a nonzero magnitude, bounded by
-9223372036854775808..9223372036854775807. Reject +1, 01, -0, whitespace, JSON numbers,
NaN and out-of-range text. No binary float or JavaScript Number conversion is used.
Integer display in this baseline is its exact canonical spelling; localized number/
date/currency formatting is a separate LOCALE-002/003 preference/adapter obligation.
A preformatted money/date remains text and does not become a plural selector.

For en/de v1, category is one exactly when the canonical integer is `1` OR `-1`,
otherwise other. This explicit magnitude rule handles signed domain counts without
passing a negative number or a narrowed value to Qt. The Qt lookup witness is
int1 for one, int2 for other. The actual integer remains its ordinary named argument;
no `%n` is inserted by generation. Zero, MIN and MAX therefore use witness2 and keep
all displayed digits. Browser selection compares canonical strings to 1/-1 using
the SAME rule; it must not coerce a signed64 value through Number/Intl.PluralRules.
The Qt en/de numerus rule n==1 selects its first form and otherwise its second;
witnesses1/2 use precisely those supported branches. Negative/magnitude semantics
are ours and do not assert that Qt accepts negative counts as plural inputs.

Ordinary messages use n=-1 (Qt's nonnumerus sentinel) and have one text form.
The witness is never a displayed count, a financial value, an approximation, a
UTC value or an authority decision. Future locales/plural systems require a focused
contract extension, not automatic reuse of this two-category rule.

## 4. Generated Qt mapping and real binary compilation

Text outputs are proposed localization/generated/qt/messages_en.ts and
messages_de.ts. They are deterministic UTF-8 WITHOUT BOM, LF line endings, one
final LF, XML declaration `<?xml version="1.0" encoding="utf-8"?>`, root
`<TS version="2.1" language="en|de" sourcelanguage="en">`.

Emit EXACTLY ONE context child under TS, beginning with an explicit EMPTY
`<name></name>`, and put ALL ID messages inside that context. No message is a direct
TS child and no nonempty context name is allowed. Actual selected Qt6.12 lrelease
rejects top-level message even though the published TS schema permits it; the
actual reader is authoritative for this selected mapping. Its QM writer selects
ID-based keys from nonempty id plus empty context. The historical -idbased flag
is a deprecated no-op and is NOT passed. A nonplural
message has `<message id="...">`; plural has `<message id="..." numerus="yes">`.
For either locale, source is the English text form or English other form. Put the
message description in `<extracomment>`. Translation has no unfinished/obsolete/
vanished type. Plural translation has exactly TWO `<numerusform>` children,
one then other; ordinary translation contains its sole text. No locations,
dependencies, source paths, timestamps or mutable application code are emitted.

Preserve the exact named-template text, including doubled braces and literal Qt-
looking percent sequences. Escape XML text &,<,> as &amp;,&lt;,&gt;, double quote
as &quot;, apostrophe as &apos;. Emit CR as `&#13;`, with literal LF/TAB allowed;
otherwise XML line-end normalization would lose an explicit source CR. Stable IDs
are ASCII but attribute escaping still follows these rules. No XML string escaping
implies HTML/QML rich-text safety.

Build binary outputs under build/<preset>/localization/messages_en.qm and
messages_de.qm. Selected LinguistTools version is EXACT6.12.0; locate the CMake
imported Qt6::lrelease tool rather than assuming a PATH alias. Proposed argv, with
paths passed as process arguments and no shell interpolation:

~~~text
<Qt6::lrelease> -fail-on-unfinished <messages_en.ts> -qm <messages_en.qm>
<Qt6::lrelease> -fail-on-unfinished <messages_de.ts> -qm <messages_de.qm>
~~~

Do NOT pass -fail-on-invalid: that checks Qt positional/%n placeholders, whereas
our placeholders use the explicitly validated shared named grammar and percent
characters are ordinary literals. Qt's corresponding validator is opt-in in6.12;
our full source/schema/template/plural validation is mandatory. No unfinished form,
failed process, missing tool, silent plural padding/removal, skip or failure inversion
counts as generated .qm acceptance. Capture actual process exit and bounded diagnostics.

Canonical TS serialization is byte-defined as follows. The XML declaration and
root opening tag each occupy one line with no leading spaces. Root attributes
are ordered version, language, sourcelanguage as above. The ONE context opens
on a two-space line. Its FIRST child is exactly four spaces then
`<name></name>` plus LF; no whitespace is part of that empty name. Messages sort
by ID, start with four ASCII spaces, and have attributes id then numerus (the
latter only for plural). Child order is source, extracomment, translation, each
indented six spaces. Ordinary source/description/translation uses its opening tag,
escaped scalar text and closing tag together, then one structural LF. A plural
translation opens on its own six-space line; one/other numerusform children each
start with eight spaces, followed immediately by escaped text and closing tag plus
LF; translation closes on a six-space line. A message closes on a four-space line;
context closes on a two-space line; root closes without leading spaces, then one
final LF. There are no blank separator lines, XML comments, DOCTYPE, namespace
declarations, self-closing tags or formatting attributes.

These indentation/newline rules apply ONLY outside element text. In any source,
extracomment, translation or numerusform, every LF/TAB and space from the actual
text remains exactly its own scalar, with no inserted continuation indentation
or line wrapping. The closing tag immediately follows the final escaped scalar,
even when the text contains newlines. Thus source `A`+LF+` B` is serialized as
`<source>A`+LF+` B</source>` after its structural opening indentation; adding
structural indentation after that LF would change the translation and is forbidden. The identical
character-by-character escaping rule applies to all text nodes.

## 5. Browser output and contributor consistency

Proposed text outputs localization/generated/web/en.json and de.json have root
EXACT keys schema_version1, locale(en/de), fallback("en"), messages(object by ID).
Each message value has EXACTLY parameters(the sorted name/type object), plural
(null/name) and forms(the text object or ordered one/other object). Editorial
translator description is omitted from runtime browser data.

Serialize with two ASCII spaces indentation, fixed object key order as specified
here, ASCII-sorted IDs/parameter names, non-ASCII scalars literal UTF-8, no BOM and
one final LF. JSON quote/backslash/controls use canonical JSON escapes; additionally
escape <,>,&,U+2028,U+2029 as lower-case \u003c/003e/0026/2028/2029. This keeps JSON
safe to transport but never authorizes innerHTML or dynamic script construction.
Actual decoded template scalar values equal the Qt selected raw strings.

The SAME generated web/en.json is also the native declaration metadata, packaged
alongside mandatory en/de .qm. This reuses one generated artifact, not a new source
or hand-maintained C++ map. Native consumers load its ID -> parameters/plural/forms
descriptors before accepting messages. The declared plural member identifies the
selector even in TC14 when no translated text contains that name; declared types
and names determine exact missing/extra/type validation and witness choice. Never
infer declarations or selector names from QM or the appearance/order of placeholders.
Qt QM does not preserve this metadata.

Native metadata parsing uses the exact generated browser schema and validates its
schema_version/locale/fallback and descriptor grammar. Metadata absence, malformed
metadata or missing mandatory English QM is catalog_unavailable. Native raw text
STILL comes from actual QM lookup, including English fallback: en.json forms are
consistency oracles/data, never a substitute runtime translation path for missing
QM. During the later native load/verification gate, every metadata ID must resolve
in English QM at n=-1 or witnesses1/2 as declared, with raw scalar strings EXACTLY
equal to en.json forms. A selected German QM is queried only using those declared
IDs/form witnesses.
An absent selected ID/form uses the verified English base. A selected QM that
cannot load, or returns a form violating the shared declared placeholder grammar,
is treated as unavailable and English is used; it never changes parameter types
or chooses another integer argument. An invalid/missing BASE pair instead yields
catalog_unavailable with no successful text. No native path substitutes the JSON
form string for the required raw QM lookup.
Generator/check and package checks compare all expected text/binary artifacts from
one authoritative source, including de.json versus actual German QM raw forms.
The later adapter/runtime/package tests must prove the metadata+QM pairing and
selector-only case; generating JSON alone never completes Qt support.

Contributors edit ONLY localization/messages.json. Generated .ts/browser JSON may
be checked in for review; .qm belongs in build/package output. All four text files
must compare byte-identically with fresh generation. Binary consistency is checked
against actual newly compiled files and repeat generation, not a JSON/TS stand-in.
Do not put independently edited desktop and web translations in separate sources.

## 6. Lookup/English fallback obligations for later adapters

Native adapter inputs are the generated web/en.json declaration metadata plus
the generated mandatory English QM and optional selected German QM. The browser
uses the generated en/de JSON descriptors/forms. For a known ID, native lookup uses direct
`QTranslator::translate("", id_utf8, nullptr, witness)` on the selected supported
locale catalog, then the generated mandatory English catalog when the selected
catalog is absent or has no matching message. It must NOT use qtTrId,
QCoreApplication::translate, qsTrId or QString::arg for this catalog. Those are
valid Qt facilities with different `%n`/parameter semantics, not this mapping.
The chosen raw template then passes through the one-pass named formatter.

English .qm must be generated, packaged and load-checked as the native base;
unsupported requested languages use it. Browser loading similarly retains generated
en as the required base. A missing/broken base yields an explicit catalog_unavailable
outcome, never the stable ID mislabeled as English translation. An unknown ID or
invalid argument gives a bounded unknown_message/invalid_arguments outcome; it does
not invent English from an ID. These are adapter obligations, not new server/wire
error schemas or implemented product flows. Packaging/actual runtime fallback is a
release gate; mandatory English data is not optional because the source language is en.

The browser/native adapters render DATA as plain text: a Qt/QML label must use
plain-text semantics, browser code must use text nodes/normal escaped bindings.
Neither translates inserted arguments or authored text. Detection, persistence,
retranslation notification, saved-choice precedence and German layouts still need
LOCALETEST-002/003/090 runtime evidence. Generator completion cannot mark them done.
