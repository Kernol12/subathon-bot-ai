## Independently checked oracles and controls

- Mixed HTTP IDs 0–3 and WebSocket IDs 4–7 require each matching committed reply,
  exact SQL IDs `[0,1,2,3,4,5,6,7]`, eight rows and sum 28. An eight-client barrier
  starts actual transport work together; this is bounded concurrency, not a load
  or performance result.
- Queued HTTP disconnect admits 41, checks no committed row while held, closes
  the client, releases and requires exactly `[41]`, count one and sum 41 after
  clean exit. This checks authoritative admission independently of reply survival.
- Closing admission preserves queued 7 and rejects later HTTP 8 / WebSocket 9;
  exact SQL `[7]`, count one and sum seven excludes either rejected contribution.
- Stop with held HTTP 11 and WebSocket 12 requires both committed replies,
  clean process exit, exact SQL `[11,12]`, count two and sum 23. The harness closes
  the WebSocket after receiving its acknowledgement, so a forced early quit cannot
  substitute for a delivered reply.
- An external listening socket retains the occupied port during child startup;
  bounded nonzero exit and no ready event are required. The test deliberately
  allows the pinned framework's fatal bind path to omit a JSON startup_failed event.
- SIGTERM follows admission of held HTTP 21 and requires its committed reply,
  zero exit, exact SQL `[21]`, count one and sum 21. Source review must separately
  verify safe signal-to-Qt handoff rather than framework/SQL calls in the handler.

The literal IDs, row lists, counts and sums are derived independently from test
inputs. Expected values are not generated by production or the probe. Direct
read-only SQLite queries check the actual database, including empty state before
releasing held commands. All six cases use distinct disposable process/database
state, loopback sockets, synthetic IDs and standard-library clients.

The bounded WebSocket client checks HTTP 101 and the RFC6455 accept value, masks
client frames, handles ping and close frames, and bounds frame size. It is scoped
to this probe's text/close traffic, not a general protocol conformance suite.
JSON stdout events and network responses establish ordering; socket/process and
monotonic deadlines bound failures without sleep-based sequencing. Cleanup kills
an unfinished child without treating that action as a successful shutdown.

## Source-review requirements and limitations

Ownership flags, policy fields and stopped flags are useful observations but cannot
prove their own implementation. Later independent code review must verify actual
runtime thread comparisons, Qt connection ownership, WAL/FULL readback, proper
callback lifetime and loop affinity, writer close/removal after framework teardown,
and genuine framework readiness. No such code approval is supplied here.

Exact pinned-source preparation found that Drogon BeginningAdvice precedes
ListenerManager::startListening, whose TcpServer::start posts listen to an I/O
loop. Therefore emitting ready directly in BeginningAdvice is insufficient; the
implementation needs actual listener readiness or an ordered I/O-loop barrier.
Pinned Trantor Socket::bindAddress exits nonzero on failed bind, supporting the
contract's no-ready/nonzero requirement without mandatory application JSON.
Drogon quit stops network I/O and force-closes listeners/connections, so queued
callbacks alone do not establish flushed replies before quit. These findings were
sent to the coordinator before the baseline was frozen.

The coordinator must capture actual intended FeatureNotImplemented response or
persistence failures from a successfully built/running stub. Missing dependencies,
launch failures, absent-event timeouts and harness errors are not intended-red
evidence; record any such results separately. If only representative cases have
an intended behavioral red run, state that scope rather than claiming all six.

No production source, existing numeric acceptance test, shared build file or
progress record was changed in this review. TLS/Caddy, remote security, public
APIs, crash recovery, backpressure, statistics-reader isolation, performance,
providers, Windows and Wayland/OBS remain unverified. Reuse as production requires
its own reviewed contracts/tests and code review.
