## Coding preferences - general

- Keep things simple.
- Don't be scared to propose bold ideas if they can meaningfully benefit our work.
- Tests are good! Endless smoke tests, "regression tests" for feature deletions, etc, much less good.
  Tests should be focused, not slop.
- Comments are a great way to clarify functionality and how code is used.
  Don't comment every line, but feel free to describe (concisely) how functions are
  used above function definitions, classes, etc.
- Keep comments up to date! When making changes, it's important to keep things in sync.
- I like to have a clean folder structure.

## Coding preferences (C++)

- If you see there is a library which already solves a problem propose it to me.

## Questions are read-only

- A question is a request for an answer, not for changes.
  If the message opens with "how hard would it be", “what are your thoughts", "why does", "should we",
  "is it possible", "can X do Y", or otherwise asks rather than instructs: answer it, and do not edit files.
- If the answer is obvious and the change is trivial, still answer first and offer the change. Ask before making it.

## Authority and purpose

Build the agreed product in `docs/specification.md` (v0.45). Start with
`docs/ARCHITECTURE.md`, `docs/AGENT_WORKFLOW.md`, `docs/TEST_STRATEGY.md`, and
`progress/state.json`. Read scoped AGENTS.md files in every module you edit.
This baseline includes scaffolding and draft tests, not completed product behavior.
Routine implementation choices are allowed within scope. Identify requirement
conflicts or proposed behavior changes explicitly; never silently shrink release scope.
Unknown provider behavior is not a supported capability.

## First assignment and test-first gate

Start with `FIRST_AGENT_PROMPT.md`: environment validation, public-contract review,
then test authoring/review and an observed failing baseline. Production implementation
of a behavior waits for its reviewed, specification-linked tests and intended red run.
Minimal interfaces/build harnesses/fakes and explicit unimplemented stubs are allowed.
A missing dependency, failed compilation or skipped test is not a valid red baseline.
The initial GoogleTest cases are DRAFT and do not yet establish independent review.

Do not delete/skip/weaken baseline assertions or change fixtures simply to make code
pass. A genuine test defect or requirement change needs a written specification-based
reason and a separate reviewer; record the revised baseline. Add meaningful regression
tests. Expected results must not be generated by the implementation under test.

## Boundaries

- C++20/Qt >=6.12 server/desktop; QML desktop UI; HTML/CSS/TypeScript browser UI.
- One server = one subathon, Linux server, Windows/Linux x86-64 clients.
- Core domain depends on neither UI nor provider/network framework code.
- Drogon request threads bridge to the authoritative Qt command/state queue.
- One controlled Qt SQL/SQLite writer; correct connection thread ownership.
- Connectors submit normalized events; no connector/client writes authoritative state.
- Separate native/browser renderers, common declarative scene contract, desktop-only full editor.
- Exact accounting, rounding/reversal provenance, cap-limited actual effects and deduplication follow the specification; no floating-point shortcut for exact money/score.
- No project-hosted authorization service. Own installation credentials where needed; validate any proposed public-client shortcut.
- Keep all seven integrations and all three exchange-rate providers in intended release scope.

## Work protocol

1. Select a dependency-ready task, claim it in `progress/state.json`, and read its brief.
2. Record scope, current contract revision, acceptance criteria and any shared-file ownership.
3. For concurrent writers use separate branches/worktrees. Coordinate schemas, migrations,
   root build files and progress state through the integrator; do not overwrite another agent's work.
4. Keep changes focused. Use repository decision records and handoffs, not chat memory alone.
5. Run checks appropriate to the change. Record exact commands, outcome and environment.
6. Update task notes, evidence and next steps; regenerate PROGRESS.html and check consistency.
7. Return a concise handoff with changed paths, decisions, checks, remaining gates and commit if available.

The tool/provider used inside CLion is not prescribed. If it does not automatically
load this file, explicitly read it at the start of the session. Do not assume a prior
conversation or IDE-specific agent memory is available.

## Commands

```sh
python3 tools/check_project.py
python3 -m unittest discover -s tests/tooling -v
python3 tools/progress.py render
python3 tools/progress.py render --check
cmake --preset scaffold-debug
cmake --build --preset scaffold-debug
ctest --preset scaffold-debug
# After GoogleTest setup and review (currently expected to FAIL on FeatureNotImplemented):
cmake --preset acceptance-debug
cmake --build --preset acceptance-debug
ctest --preset acceptance-debug -L acceptance
```

`scaffold-debug` checks infrastructure only. `acceptance-debug` includes draft red
feature tests and must not be relabeled as a passing product suite. Do not use
WILL_FAIL, blanket continue-on-error, or baseline skipping to hide acceptance failures.
Qt probe: configure/build/test `qt-probe-debug` with Qt >=6.12 discoverable.
Use `CMakeUserPresets.json` for personal paths; never commit machine-specific IDE settings.

## Evidence and status

Distinguish planned, authored, independently reviewed, observed red, implemented,
simulation-tested and live/platform-verified. Do not claim commands ran when they did
not. A test-author task can finish with reviewed tests and documented intended red;
this does not finish the feature. `done` implementation tasks require passing relevant
acceptance checks plus separate review, and can still leave explicit release gates.
Never invent a verification percentage or turn unknown source fields into known values.

Default tests use synthetic/redacted fixtures, fake adapters and separate disposable
state. Keep real credentials and supporter data out of source, fixtures, reports and
HTML. Live provider checks are separate documented operations; do not send chat or
process live contributions as a side effect of default tests.

## Style

Use existing CMake targets/presets, C++ namespaces and .clang-format. Prefer small,
explicit interfaces, RAII and owned dependencies. Keep implementation details out of
product UI. Keep UI labels translatable; English/German and Light/Dark/System remain
required. Preserve GPL-3.0-or-later and dependency notices. Avoid new dependencies
where existing selected tools suffice; record justified additions and version pins.
